# 본인 승인 대기 요청 수정

변경 요청 목록에서 본인의 대기 요청을 펼치고 **내 요청 수정**을 누른다. 변경 사유와 제안값을 수정할 수 있으며, 주문 요청에는 입금 상태·입금일·출고 상태·출고일이 함께 표시된다. 전체 주문 요청의 품목 추가·삭제·수정도 가능하다. 승인·반려가 끝난 요청과 타인의 요청은 수정할 수 없다.

주문 목록의 입금 표시 또는 출고 상태를 누르면 통합 상태 변경 창이 열린다. 해당 주문에 본인이 제출한 대기 요청이 한 건 있으면 그 요청을 보완한다. 여러 건이면 임의로 합치지 않고 변경 요청 목록에서 선택하도록 안내한다. 주문 상세/RAW 수정도 기존 대기 요청을 우선 사용한다.

수정해도 확정 주문 및 동기화는 바뀌지 않는다. 서버가 기존 검증을 트랜잭션 안에서 시험 실행하고 롤백한 뒤 요청 내용과 버전만 저장한다. 이전 제안값·사유는 비공개 이력에 남는다. 관리자가 열어 본 버전과 실제 버전이 다르면 승인·반려를 거절하여 다시 검토하게 한다. 구버전 브라우저는 수정된 요청을 처리할 수 없다.

## 배포

- 기존 `sql/change-approvals.sql`, `sql/invoice-number-allocation.sql` 적용 후 `sql/request-revisions.sql`을 한 번 적용한다. 운영 적용명: `own_pending_request_revisions` (2026-09-29).
- 프론트: `request-editor.js/css`, `admin-approvals.js`, `admin.html`, `app.js`, `index.html`을 함께 배포한다.
- 기존 요청의 내용과 처리 상태는 변경하지 않는다. 새 이력 테이블에는 직접 접근 권한이나 RLS 허용 정책이 없으며, 본인/관리자 검증을 거친 조회 RPC로만 이력을 볼 수 있다. 이에 대한 `rls_enabled_no_policy` INFO는 의도한 비공개 접근 모델이다.
- 본인 대기 요청의 대상과 원본 스냅샷은 고정한다. 같은 주문의 부분 수정 요청을 전체 주문 수정으로 보완할 때만 대상 ID와 주문 원본 일치를 확인한 뒤 새 품목 원본도 검증한다. 이미 확정 자료가 바뀌었다면 `STALE_DATA`로 중단한다.

## 검증

전체 Node 테스트 355개 통과, JS 구문 검사 통과. PGlite에서 소유자/외부 사용자/익명 접근, 승인된 건 수정 거부, 변경 전 원장 유지, 이력 보존, 오래된 편집·승인 거부, 부분 요청의 전체 주문 보완, 주문·출고 동시 반영을 확인했다. 합성 브라우저 화면에서 Paid 요청에 출고완료와 출고일을 추가하여 한 요청의 버전만 증가하는 것을 확인했다. 실제 팀원 요청을 테스트 목적으로 수정하거나 승인하지 않았다.
